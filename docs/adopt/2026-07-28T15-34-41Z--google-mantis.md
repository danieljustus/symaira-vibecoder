## Verdict

`symvibe` is a much better match for `google/mantis` than the previous target
(`symaira-guard`) turned out to be: both are deterministic Go/orchestration
layers that drive an LLM coding agent through a multi-step, stateful workflow —
`symvibe`'s cycle engine is structurally close to what Mantis's own README
recommends teams build *on top of* its raw meta-agent loop ("Building
Deterministic Pipelines (Production-Grade)"). Most of Mantis's actual content
is already superseded by `symvibe`'s existing design (model-per-step bindings
with fallback chains, a persisted/resumable step scheduler, sensor-based
auto-skip). The real value here is narrower and sharper: Mantis's discipline
around **never letting automated recovery discard local work** exposes a
concrete, currently untested data-loss path in `symvibe`'s own recipe
`review_mode`, and its verification-outcome modeling suggests how to wire the
already-defined but currently dormant `needs_review` step status.

## What we already do as well or better

- Mantis's "Building Deterministic Pipelines" section recommends wrapping the
  raw meta-agent loop in a deterministic programmatic orchestrator for
  production use (`README_AGENTS.md` "Building Deterministic Pipelines
  (Production-Grade)") → `symvibe` **is** that deterministic orchestrator
  natively (`internal/engine/engine.go`, `docs/ARCHITECTURE.md` "Layers") — no
  raw LLM-driven meta-loop to wrap in the first place.
- Mantis's "Model Selection & Efficiency Guidelines" (`README_AGENTS.md:593-620`)
  is advisory prose recommending cheap models for triage and flagship models
  for hard stages → `symvibe` already has this as an actual config schema:
  per-step/per-category model bindings with `fallback_models` chains and a

  `symvibe`'s CI already runs lint/vet/tests with an explicit coverage
  threshold (`e5b418f coverage: add focused tests and explicit 58% repo
  threshold`), unrelated to but at least as rigorous as Mantis's Tier-1 lint.

## Findings

- [ ] **[Security] Recipe review_mode's workspace restore is destructive and untested**
  - **Status quo:** `internal/recipe/service.go:170-188` (`restoreWorkspace`) runs `git checkout HEAD -- .` followed by an unconditional `git clean -fd` directly against the **live** workspace, then re-applies only the pre-run diff of *tracked* files (`snapshotDiff`, `internal/recipe/service.go` uses `git diff --no-ext-diff HEAD`, which never sees untracked files). Any file that existed *before* the run but was untracked in git (scratch files, local overrides, anything not yet `git add`ed) is silently and irrecoverably deleted by `git clean -fd` when `review_mode=true` — the pre-run snapshot never captured it, so there is nothing to restore. All three restore commands ignore their errors (`_ = cmd.Run()`), and `RecipeResult` (`internal/recipe/contract.go:52-63`) has no field to report whether the restore actually succeeded. No test in `internal/recipe/*_test.go` exercises this path (no test references `restoreWorkspace`, `clean -fd`, or an untracked file at all) — this is a shipped, versioned contract (`SchemaVersion = "1"`, already wired for "vault workflows" per `669b301 feat(recipe): add reviewed recipe runner contract for vault automation (#99)`), not a prototype. Upstream `google/mantis` was built around the exact opposite discipline for the same problem — running an agent against a workspace it must not corrupt: its boundary-sync step is documented as "strictly non-destructive: it is skipped entirely if the tree is dirty, ahead of upstream, on a detached HEAD, or has no upstream, and it **never** runs `git reset --hard`, `git checkout -- .`, `git clean`, `hg update -C`, or anything else that discards local work" (`README_AGENTS.md:287-290`), and separately pins an isolated copy under `.mantis_snapshots/` *before* any stage touches the target rather than resetting the live tree afterward (`README_AGENTS.md` "The Snapshot Model").
  - **Proposed solution:** Pattern adoption only (no code copied). Two changes, either sufficient on its own, ideally both: (1) make `snapshotDiff` also record the set of untracked paths present before the run (`git status --porcelain` filtered to `??`) and refuse `review_mode` (return an error) rather than silently deleting them if any exist that the run didn't create itself; (2) prefer running the recipe against an isolated copy (e.g. `git worktree add` into a temp directory, mirroring Mantis's pinned-snapshot approach) instead of resetting the live workspace after the fact, so a mid-run failure or crash can never leave the *live* tree touched at all. At minimum, stop swallowing the restore commands' errors and surface a `restore_status` field on `RecipeResult` so a caller (SymDesk, a vault workflow) can detect a failed/incomplete restore instead of assuming success.
  - **Effort/Impact:** Medium effort (git-worktree-based isolation) or low effort (just the untracked-file guard + error surfacing) / high impact — this is a real, currently-unguarded data-loss path in an API already used for automation against real repositories.

- [ ] **[Architecture] Wire the dormant `needs_review` status to a declarative per-step risk rule**
  - **Status quo:** `internal/config/cycle.go:86` defines `StatusNeedsReview`, and `internal/engine/status.go:17-34` already permits every transition into and out of it — but nothing in the engine ever *sets* a step to `needs_review` automatically; it is reachable only via a manual GUI-initiated write (`internal/engine/status.go:5-7`'s own doc comment: "doubles as a safety net for GUI-initiated status writes"). `docs/ARCHITECTURE.md` "Roadmap (not in the MVP)" lists this explicitly as unbuilt: "`needs_review` halt + an explicit human-ack affordance for high-risk steps (release, force-merge)." The step schema already has one declarative per-step rule shape to model this on: `auto_skip = { sensor, when }` (`internal/engine/sensors.go:16-21`, cheap probe + predicate → automatic status change).
  - **Proposed solution:** Pattern adoption only. Add a symmetrical declarative rule, e.g. `requires_review = { when: "category == release" }` or a simple `high_risk = true` step flag, evaluated by the engine right after a step reaches `done` (mirroring how `auto_skip` is evaluated right before a step runs) — on match, transition to `needs_review` instead of letting the cycle auto-advance, and require the existing GUI "human ack" transition (`needs_review → done`) before `NextRunnable` proceeds. This mirrors Mantis's own insistence that consequential, hard-to-reverse actions get an explicit human gate rather than being folded into an unattended pass (`README_AGENTS.md` "Patch Verification and Re-attack Constraints" — `VERIFIED_SECURE` is only ever set after an explicit, bounded verification step, never assumed) and reuses the `category` concept `symvibe` already has for model bindings instead of inventing a second risk taxonomy.
  - **Effort/Impact:** Medium effort (one new step-schema field + one engine check, both mirroring existing `auto_skip` code) / medium-high impact — closes a roadmap item `symvibe` has already recorded wanting, specifically for the two step categories (release, force-merge) the same roadmap line names.

- [ ] **[Architecture] Design the planned run-history store as structured learnings, not just a log**
  - **Status quo:** `docs/ARCHITECTURE.md` "Roadmap (not in the MVP)" lists "SQLite `RunState` for cross-execution history / audit" with no further design — currently the cycle only tracks the *current* status per step (`internal/config/cycle.go`), nothing about *why* a prior run of the same step failed or what a human corrected. There is no equivalent today, and no test/code assumes a shape for this yet, so this is the moment to decide the schema before it exists rather than after. Upstream `google/mantis` solves an analogous problem — improving future passes over repeated failures — not with a plain audit log but with a dedicated stage (`mantis-reflect`) that parses execution trajectories and appends *structured* insights (false assumptions, tool failures, successes) to `workspace/learnings.jsonl` (`mantis-reflect/SKILL.md:1-16`), which downstream stages then actively consult rather than a human having to read a log.
  - **Proposed solution:** Pattern adoption only. When `RunState` is designed, give it a `learnings`-shaped table (or column) alongside the raw run log: per failed/needs_review step, a short structured record of *why* (sensor value, backend error class, human correction if any) — not free-text logs. `Cycle.NextRunnable`/the Resolver could then use it the same way Mantis's planner consults `historical_learnings.jsonl`: e.g. surfacing "this step failed twice with the same backend error" in the board UI, or letting a `fallback_models` chain trigger earlier if history shows the primary model repeatedly fails this step's category.
  - **Effort/Impact:** Low effort now (a schema decision, not implementation — the feature has no code yet) / medium impact — cheap to get right before `RunState` ships, expensive to retrofit afterward once the board UI and API depend on a plain-log shape.

## Considered and rejected

- **Full 16-stage vulnerability-discovery pipeline (plan → research → dedupe → review → critic → reproduce → patch → calibrate → reflect → report)** — gate 3 (Better): `symvibe` already *is* the deterministic orchestrator Mantis's own docs recommend building on top of this pipeline; there is no raw LLM-orchestration loop here to replace, and `symvibe`'s domain (drive any coding-agent backend through a general dev cycle) is broader than Mantis's narrow security-review pipeline.
- **Meta-Agent long-lived, chat-steerable supervisor session** — gate 3 (Better)/scale fit: `symvibe`'s board already gives Pause/Resume/Cancel plus a live SSE activity feed (`README.md` "Autonomie", `docs/ARCHITECTURE.md` "load-bearing flow") as its interactive-steering equivalent; a persistent unattended multi-day supervisor session contradicts `symvibe`'s own stated security posture ("Loopback-only, unauthenticated — only use locally," `SECURITY.md`), which is the opposite of Mantis's target deployment (hardened, unattended cloud VM).
- **Structural code index with graceful backend degradation (SCIP/Kythe → compiler → AST → ctags → grep)** — gate 1 (Transferable): built to ground an LLM's own code reading. `symvibe` never reads target code itself — every backend (opencode/aider/claudecode/cline/local_api) does its own code grounding; there is nothing in `symvibe`'s own code to ground.
- **Marginal-capability risk-scoring catalogue (mantis-calibrate)** — gate 1 (Transferable): scores discovered *vulnerabilities*; `symvibe` has no equivalent artifact (a cycle step is not a security finding) to score this way.
- **Unattended cloud deployment hardening (VPC-SC, custom least-privilege IAM role, `--dangerously-skip-permissions` gating)** — gate 1 (Transferable): `symvibe` explicitly targets local, loopback-only operation (`SECURITY.md`); the unattended-cloud threat model this section defends against does not apply to its deployment model.
- **`npx skills add <repo>`-style skill installer / mdformat pre-commit discipline for skill files** — gate 2 (New)/out of scope: `symvibe` invokes skills by name (`$00-sync`) but does not author or ship `SKILL.md` content itself — that responsibility (and the better `gh-adopt` target for it) belongs to `symaira-skills`, not `symaira-vibecoder`.
- **Tiered Evaluation Strategy for prompts/skill files (static → unit → golden-dataset)** — gate 2 (New)/out of scope: same reasoning — `symvibe` consumes skills, it does not define or evaluate their prompt content.

## Open questions

- Whether `internal/recipe`'s current callers (SymDesk, vault workflows per the `#99` commit) already work around the untracked-file deletion risk by convention (e.g. always calling recipes against a workspace known to have no untracked files) — if so the fix is still worth making explicit and tested, but the real-world blast radius today may be smaller than the code alone suggests. Settling this needs a look at the actual caller code, which is outside this repo.
- Whether a `git worktree`-based isolation for `review_mode` is compatible with backends that expect to run *inside* the caller's exact working directory (some coding-agent CLIs shell out to project-local tooling, e.g. a Makefile or virtualenv, that may not exist identically in a worktree checkout) — needs a quick spike against at least the `opencode` and `aider` backends before committing to that shape.

Best first step: fix the untracked-file deletion path in `review_mode` (`internal/recipe/service.go:170-188`) — it is the one finding here with a concrete, currently-live data-loss failure mode.
